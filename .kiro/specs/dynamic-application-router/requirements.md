# Requirements Document

## Introduction

The Dynamic Application Router (`psmcp-router-dynamic-app`) is a new PS-MCP router package that extracts and reworks the "open map" functionality currently in the ArcGIS router. The router implements the MCP Apps standard — an official MCP extension that allows tools to return interactive UI components rendered directly in MCP-compatible clients (Claude Desktop, ChatGPT, Goose, VS Code, and others).

Instead of generating unique HTML per request and storing state in memory, the new router uses the MCP Apps pattern: tools return structured data (map parameters) and reference a static resource URI. The static HTML/JS viewer application receives the tool result data via the MCP Apps SDK and dynamically renders the appropriate map. Crucially, the Map Viewer App registers its own app-side tools (e.g., `add_layer`, `change_basemap`, `update_symbology`) that the model can call on the running app instance to incrementally update the map without creating a new one. For LLM-based customizations, the tool calls the LLM to generate a JavaScript customization snippet that is passed as part of the structured content and executed by the static viewer app.

## Glossary

- **Dynamic_App_Router**: The new FastMCP router instance (`psmcp-router-dynamic-app`) that provides MCP Apps tools and resources for generating dynamic HTML map applications.
- **MCP_Apps**: The official MCP extension standard that enables tools to return interactive UI components rendered in sandboxed iframes within MCP clients. Uses `_meta.ui.resourceUri` to link tools to UI resources.
- **MCP_Client**: Any Model Context Protocol client that supports MCP Apps (Claude Desktop, ChatGPT, Goose, VS Code, Microsoft Copilot Studio, or other MCP-compatible applications).
- **Map_Viewer_App**: A static HTML/JavaScript application served as a `ui://` resource that uses the MCP Apps SDK to receive tool result data, dynamically render ArcGIS maps, and register app-side tools that the model can call to incrementally update the map (add layers, change symbology, etc.) without creating a new app instance.
- **App_Side_Tool**: A tool registered by the Map_Viewer_App via `app.registerTool()` that the host/model can call on the running app instance to modify the map state (e.g., `add_layer`, `remove_layer`, `change_basemap`, `update_symbology`, `get_current_view`).
- **Tool_Result_Data**: The structured content returned by a tool containing map parameters (type, webmap_id, layer_urls, portal_url, customization_script, etc.) that the Map_Viewer_App uses to render the map.
- **Customization_Script**: A JavaScript code snippet generated by the LLM_Backend based on `additional_requirements`, passed as part of Tool_Result_Data and executed by the Map_Viewer_App to customize the map display.
- **LLM_Backend**: An OpenAI-compatible API (standard OpenAI or Azure OpenAI) used to generate Customization_Script code based on natural language requirements and ArcGIS Maps SDK documentation.
- **Token_Resolver**: The `resolve_token()` utility from `psmcp.core.auth` that resolves ArcGIS authentication tokens from explicit parameters, auth context, or environment variables.
- **Resource_URI**: A static, predictable URI using the `ui://` scheme (e.g., `ui://dynamic-app/map-viewer.html`) that identifies the Map_Viewer_App resource.
- **Content_Security_Policy**: A set of domain allowlists (connect, resource, script, style) included in tool metadata that MCP clients use to sandbox the rendered iframe.

## Requirements

### Requirement 1: Package Structure and Router Registration

**User Story:** As a developer, I want the dynamic application router to be a standalone installable package following established PS-MCP conventions, so that it can be discovered, enabled, and deployed independently.

#### Acceptance Criteria

1. THE Dynamic_App_Router SHALL be packaged as `psmcp-router-dynamic-app` under the `packages/` directory containing at minimum: `pyproject.toml`, `README.md`, and `src/psmcp_router_dynamic_app/` with `__init__.py` and a service module.
2. THE Dynamic_App_Router SHALL declare a `psmcp.routers` entry point in `pyproject.toml` under the group `psmcp.routers` with a key of `dynamic_app` and a value referencing the router's `FastMCP` instance as `psmcp_router_dynamic_app:<router_variable>`.
3. THE Dynamic_App_Router SHALL declare `requires-python = ">=3.13,<3.14"` and depend on `ps-mcp>=0.1.0,<1.0` and `openai>=2.6.1,<3` as runtime dependencies in `pyproject.toml`.
4. THE Dynamic_App_Router SHALL use `hatch-vcs` for tag-driven versioning with `raw-options = { root = "../.." }` pointing to the monorepo root and a `version-file` of `src/psmcp_router_dynamic_app/_version.py`.
5. THE Dynamic_App_Router SHALL export the router `FastMCP` instance and `__version__` from its `__init__.py` via `__all__`, falling back to `"0.0.0+unknown"` when `_version.py` is not yet generated.

### Requirement 2: MCP Apps Compliant Tool Design

**User Story:** As an MCP client developer, I want the tools to follow the MCP Apps standard so that any MCP Apps-capable client can render the interactive map UI.

#### Acceptance Criteria

1. WHEN a map tool is invoked, THE Dynamic_App_Router SHALL return a tool result containing a text content block with a human-readable description and a JSON-encoded structured content block conforming to the Tool_Result_Data schema (map type, configuration fields per Requirement 11, and optional Customization_Script).
2. WHEN a map tool is invoked, THE Dynamic_App_Router SHALL include `_meta.ui.resourceUri` in the tool result set to `ui://dynamic-app/map-viewer.html`.
3. THE Dynamic_App_Router SHALL include Content_Security_Policy information in the tool result `_meta.ui.csp` field specifying connect-src, script-src, style-src, and img-src directives with allowlists that include ArcGIS CDN domains (js.arcgis.com, services.arcgisonline.com, basemaps.arcgis.com, cdn.arcgis.com, static.arcgis.com).
4. THE Dynamic_App_Router SHALL use a single static Resource_URI (`ui://dynamic-app/map-viewer.html`) for all map tools, with the tool result data determining what is rendered.
5. THE Dynamic_App_Router SHALL NOT store per-request state in memory — all information needed to render the map SHALL be contained in the Tool_Result_Data.
6. WHEN a map tool is invoked with parameters referencing additional domains (portal URLs or layer service URLs), THE Dynamic_App_Router SHALL dynamically add those domains to the Content_Security_Policy connect-src and img-src allowlists in the tool result.

### Requirement 3: Static Map Viewer Application Resource

**User Story:** As an MCP client, I want to read the static map viewer resource and render it in an iframe, so that it can dynamically display maps based on tool result data.

#### Acceptance Criteria

1. THE Dynamic_App_Router SHALL register a resource at `ui://dynamic-app/map-viewer.html` that serves the Map_Viewer_App as a single self-contained HTML file where all application JavaScript and CSS are inline within the document and no server-hosted file dependencies exist beyond CDN-loaded libraries (ArcGIS Maps SDK, MCP Apps SDK).
2. THE Map_Viewer_App SHALL use the MCP Apps SDK (`@modelcontextprotocol/ext-apps`) to receive Tool_Result_Data from the host via the `ontoolresult` callback.
3. THE Map_Viewer_App SHALL use the ArcGIS Maps SDK for JavaScript (Web Components) to render maps based on the received parameters.
4. THE Map_Viewer_App SHALL support rendering three map types based on the `type` field in Tool_Result_Data: `sample_map` (basemap only), `webmap` (from portal item ID), and `layers_map` (from layer URLs). IF the `type` field is missing or contains an unrecognized value, THEN THE Map_Viewer_App SHALL display an error message indicating the unsupported map type.
5. THE Map_Viewer_App SHALL return the same HTML content on every read — the resource is static and deterministic.
6. THE Map_Viewer_App resource content SHALL be served with MIME type `text/html;profile=mcp-app`.
7. IF Tool_Result_Data contains a `customization_script` field, THEN THE Map_Viewer_App SHALL execute the script as a JavaScript function body after the base map has been initialized and rendered.

### Requirement 4: Sample Map Tool

**User Story:** As an LLM user, I want to open a simple ArcGIS sample map, so that I can visualize geographic data with a default basemap.

#### Acceptance Criteria

1. THE Dynamic_App_Router SHALL provide an `open_sample_map` tool that accepts an optional `additional_requirements` string parameter with a maximum length of 2000 characters.
2. WHEN `open_sample_map` is called without `additional_requirements`, THE Dynamic_App_Router SHALL return Tool_Result_Data containing `{"type": "sample_map"}` and a text content string that confirms a sample map is being opened.
3. WHERE `additional_requirements` is provided and `USE_ARCGIS_LLM` is set to `"true"`, THE Dynamic_App_Router SHALL call the LLM_Backend to generate a Customization_Script and include it in the Tool_Result_Data.
4. WHEN the Map_Viewer_App receives Tool_Result_Data with type `sample_map`, THE Map_Viewer_App SHALL render a topo-vector basemap centered on the contiguous United States (approximately latitude 39, longitude -98) at a zoom level that displays the full country extent.
5. IF `additional_requirements` is provided and `USE_ARCGIS_LLM` is not enabled, THEN THE Dynamic_App_Router SHALL include the `additional_requirements` text in Tool_Result_Data without a Customization_Script.

### Requirement 5: Web Map Tool

**User Story:** As an LLM user, I want to open an ArcGIS web map by its item ID, so that I can view portal-hosted maps.

#### Acceptance Criteria

1. THE Dynamic_App_Router SHALL provide an `open_webmap` tool that accepts a required `webmap_id` parameter (a non-empty string), an optional `portal_url` parameter, and an optional `additional_requirements` parameter.
2. IF `portal_url` is not provided, THEN THE Dynamic_App_Router SHALL fall back to the `ARCGIS_PORTAL_URL` environment variable.
3. IF neither `portal_url` nor `ARCGIS_PORTAL_URL` is available, THEN THE Dynamic_App_Router SHALL return an error result with `isError: true` indicating that a portal URL is required.
4. WHEN `open_webmap` is called with a non-empty `webmap_id` and a resolved portal URL, THE Dynamic_App_Router SHALL return Tool_Result_Data containing `type` set to `webmap`, the `webmap_id`, `portal_url`, and optional authentication token obtained via Token_Resolver.
5. WHERE `additional_requirements` is provided and `USE_ARCGIS_LLM` is set to `"true"`, THE Dynamic_App_Router SHALL call the LLM_Backend to generate a Customization_Script and include it in the Tool_Result_Data.
6. WHEN the Map_Viewer_App receives Tool_Result_Data with type `webmap`, THE Map_Viewer_App SHALL load and display the web map identified by `webmap_id` from the portal specified by `portal_url`.
7. IF `webmap_id` is empty or contains only whitespace, THEN THE Dynamic_App_Router SHALL return an error result with `isError: true` indicating that a valid web map item ID is required.

### Requirement 6: Layers Map Tool

**User Story:** As an LLM user, I want to open a map with multiple data layers from ArcGIS Server URLs, so that I can visualize specific feature services and map services.

#### Acceptance Criteria

1. THE Dynamic_App_Router SHALL provide an `open_layers_map` tool that accepts a required `layer_urls` list (minimum 1 URL, maximum 50 URLs), an optional `layer_where_clauses` list, and an optional `additional_requirements` parameter.
2. WHEN `open_layers_map` is called with valid parameters, THE Dynamic_App_Router SHALL return Tool_Result_Data with `type` set to `layers_map`, containing the layer_urls, where_clauses, and optional authentication token.
3. WHERE `additional_requirements` is provided and `USE_ARCGIS_LLM` is enabled, THE Dynamic_App_Router SHALL call the LLM_Backend to generate a Customization_Script and include it in the Tool_Result_Data.
4. WHEN the Map_Viewer_App receives Tool_Result_Data with type `layers_map`, THE Map_Viewer_App SHALL render each URL from `layer_urls` as a visible layer on the map.
5. WHERE `layer_where_clauses` is provided in Tool_Result_Data, THE Map_Viewer_App SHALL apply each where clause to the layer at the same index position in `layer_urls` (first clause to first URL, second clause to second URL, and so on).
6. IF `layer_where_clauses` is provided and its length does not equal the length of `layer_urls`, THEN THE Dynamic_App_Router SHALL return a tool result with `isError: true` and an error message indicating the lists must be the same length.

### Requirement 7: LLM-Based Customization Script Generation

**User Story:** As a system operator, I want the router to optionally use an LLM to generate JavaScript customization code based on natural language requirements, so that maps can be tailored to specific visualization needs without generating entire HTML pages.

#### Acceptance Criteria

1. WHEN `additional_requirements` is provided and the `USE_ARCGIS_LLM` environment variable is set to `"true"`, THE Dynamic_App_Router SHALL call the LLM_Backend to generate a Customization_Script within 60 seconds.
2. THE LLM_Backend SHALL generate a JavaScript function body (maximum 50,000 characters) that the Map_Viewer_App can execute after the base map is initialized, using the ArcGIS Maps SDK Web Components API and the `$arcgis.import()` pattern for module imports.
3. THE LLM_Backend SHALL use a system prompt containing ArcGIS Maps SDK Web Components documentation (component names, attributes, event patterns, and layer loading examples) to guide code generation.
4. IF `AZURE_OPENAI` is set to `"true"`, THEN THE LLM_Backend SHALL use the Azure OpenAI client configured via `OPENAI_KEY`, `OPENAI_BASE_URL`, `AZURE_OPENAI_API_VERSION`, and `AZURE_OPENAI_DEPLOYMENT` environment variables; otherwise THE LLM_Backend SHALL use the standard OpenAI client configured via `OPENAI_KEY`, `OPENAI_BASE_URL`, and `OPENAI_MODEL`.
5. IF the LLM_Backend call fails due to a network error, timeout, invalid API response, or missing `OPENAI_KEY`, THEN THE Dynamic_App_Router SHALL return Tool_Result_Data without a `customization_script` field and log a warning at WARNING level including the error context.
6. IF `USE_ARCGIS_LLM` is not set to `"true"` and `additional_requirements` is provided, THEN THE Dynamic_App_Router SHALL include the `additional_requirements` text in the `additional_requirements` field of Tool_Result_Data without calling the LLM_Backend.
7. THE LLM_Backend SHALL strip markdown code block delimiters (` ```html `, ` ``` `) from the LLM response before returning the Customization_Script.

### Requirement 8: Authentication Token Injection

**User Story:** As a user accessing secured ArcGIS services, I want authentication tokens to be included in the tool result data, so that the Map_Viewer_App can register them with IdentityManager for secured layer access.

#### Acceptance Criteria

1. WHEN generating Tool_Result_Data for a web map or layers map, THE Dynamic_App_Router SHALL call Token_Resolver with `required=False` to obtain the current ArcGIS token without raising an error if unavailable.
2. WHERE a token is available, THE Dynamic_App_Router SHALL include the token in the `token` field and a list of server registration URLs in the `token_servers` field of the Tool_Result_Data, where server URLs are derived by extracting the web adaptor base path (scheme + host + first path segment before `/rest`) from the portal URL and each layer URL.
3. WHEN the Map_Viewer_App receives Tool_Result_Data containing a `token` field and a `token_servers` field, THE Map_Viewer_App SHALL register the token with ArcGIS IdentityManager for each URL in `token_servers` before initiating any secured layer loading.
4. WHILE no token is available, THE Dynamic_App_Router SHALL omit the `token` and `token_servers` fields from Tool_Result_Data.
5. WHILE no `token` field is present in Tool_Result_Data, THE Map_Viewer_App SHALL load layers without authentication.

### Requirement 9: Content Security Policy in Tool Metadata

**User Story:** As an MCP client that supports sandboxing, I want CSP metadata included in the tool result, so that I can enforce security boundaries when rendering the Map_Viewer_App iframe.

#### Acceptance Criteria

1. THE Dynamic_App_Router SHALL include Content_Security_Policy in the `_meta.ui.csp` field of every tool result as a JSON object containing `connectDomains`, `resourceDomains`, `scriptDomains`, and `styleDomains` arrays.
2. THE Content_Security_Policy SHALL include the following ArcGIS CDN domains in the baseline allowlists: `js.arcgis.com` in connectDomains, resourceDomains, scriptDomains, and styleDomains; `services.arcgisonline.com` and `basemaps.arcgis.com` in connectDomains; `cdn.arcgis.com` and `static.arcgis.com` in connectDomains and resourceDomains.
3. WHEN a web map tool includes a portal URL, THE Content_Security_Policy SHALL extract the origin (scheme and host) from the portal URL and add it to the `connectDomains` and `resourceDomains` arrays if not already present.
4. WHEN a layers map tool includes layer URLs, THE Content_Security_Policy SHALL extract the origin (scheme and host) from each layer URL and add each unique origin to the `connectDomains` and `resourceDomains` arrays if not already present.

### Requirement 10: Removal from ArcGIS Router

**User Story:** As a maintainer, I want all map-opening functionality removed from the ArcGIS router, so that there is no duplication and the ArcGIS router focuses on portal search, item info, and group listing.

#### Acceptance Criteria

1. WHEN the Dynamic_App_Router is complete, THE `psmcp-router-arcgis` package SHALL NOT contain the `open_sample_map`, `open_webmap`, or `open_layers_map` tools.
2. WHEN the Dynamic_App_Router is complete, THE `psmcp-router-arcgis` package SHALL NOT contain the `get_error_page`, `get_sample_map`, `get_map_with_webmap_id`, or `get_map_with_layer_urls` resources.
3. WHEN the Dynamic_App_Router is complete, THE `psmcp-router-arcgis` package SHALL NOT contain the `arcgis_llm.py` or `arcgis_resources.py` modules.
4. WHEN the Dynamic_App_Router is complete, THE `psmcp-router-arcgis` package SHALL NOT depend on the `openai` package.
5. THE `psmcp-router-arcgis` package SHALL retain the following tools as registered and callable: `get_user_info`, `search_portal`, `list_user_groups`, `get_item_info`, and `list_system_services`.
6. WHEN the map-opening tools are removed, THE `arcgis_enterprise_prompt` prompt SHALL NOT reference the `open_sample_map`, `open_webmap`, or `open_layers_map` tools in its output text.

### Requirement 11: Tool Result Data Schema

**User Story:** As a developer integrating with the Map_Viewer_App, I want a well-defined schema for Tool_Result_Data, so that the viewer app can reliably parse and render any map configuration.

#### Acceptance Criteria

1. THE Tool_Result_Data SHALL be a JSON object with a required `type` field whose value is one of `sample_map`, `webmap`, or `layers_map`.
2. IF `type` is `webmap`, THEN THE Tool_Result_Data SHALL include a `webmap_id` field (non-empty string) and a `portal_url` field (non-empty string containing a valid URL).
3. IF `type` is `layers_map`, THEN THE Tool_Result_Data SHALL include a `layer_urls` field (array of 1 to 50 non-empty URL strings) and optionally a `layer_where_clauses` field (array of strings whose length equals the `layer_urls` array length).
4. IF `type` is `sample_map`, THEN THE Tool_Result_Data SHALL require no fields beyond `type` and the optional common fields defined in criteria 5, 6, and 7.
5. THE Tool_Result_Data SHALL optionally include a `token` field (non-empty string) and a `token_servers` field (array of 1 or more URL strings); if `token` is present then `token_servers` SHALL also be present.
6. THE Tool_Result_Data SHALL optionally include a `customization_script` field (string, maximum 50,000 characters) containing JavaScript code to execute after map initialization.
7. THE Tool_Result_Data SHALL optionally include an `additional_requirements` field (string, maximum 2,000 characters) containing the original natural language requirements text.
8. IF the `type` field is missing or contains a value other than `sample_map`, `webmap`, or `layers_map`, THEN THE Map_Viewer_App SHALL treat the Tool_Result_Data as malformed and display an error message indicating the unrecognized map type.

### Requirement 12: Error Handling

**User Story:** As an MCP client, I want clear error responses when tool invocations fail, so that the LLM can communicate issues to the user.

#### Acceptance Criteria

1. IF a tool receives invalid parameters (missing required fields, empty layer_urls list, invalid field types), THEN THE Dynamic_App_Router SHALL return a tool result with `isError: true` and an error message indicating which parameter failed validation and the reason for rejection.
2. IF the LLM_Backend fails to generate a Customization_Script, THEN THE Dynamic_App_Router SHALL proceed without the script and log a warning at WARNING level.
3. THE Dynamic_App_Router SHALL log all errors with context (tool name, parameters, error details) at the ERROR level using lazy formatting.
4. IF the Map_Viewer_App receives Tool_Result_Data that is missing the required `type` field, contains an unrecognized `type` value, or is missing required fields for the given type as defined in the Tool_Result_Data schema, THEN THE Map_Viewer_App SHALL display a visible error message indicating the nature of the parsing failure.
5. IF the Map_Viewer_App encounters a rendering error while loading map layers or initializing the map component, THEN THE Map_Viewer_App SHALL display a visible error message indicating which operation failed.

### Requirement 13: Incremental Map Updates via App-Side Tools

**User Story:** As an LLM user, I want to ask for changes to an existing map (add a layer, change symbology, switch basemap) and have those changes applied to the running map without creating a new one, so that I can iteratively build up a visualization through conversation.

#### Acceptance Criteria

1. THE Map_Viewer_App SHALL register app-side tools via `app.registerTool()` after initialization that the host/model can call to modify the running map instance.
2. THE Map_Viewer_App SHALL register an `add_layer` tool that accepts a layer URL and optional definition expression, and adds the layer to the existing map without replacing other layers.
3. THE Map_Viewer_App SHALL register a `remove_layer` tool that accepts a layer index or URL and removes the specified layer from the map.
4. THE Map_Viewer_App SHALL register a `change_basemap` tool that accepts a basemap name (e.g., "satellite", "topo-vector", "streets") and switches the map's basemap without affecting operational layers.
5. THE Map_Viewer_App SHALL register an `update_symbology` tool that accepts a layer index or URL and a renderer definition (as JSON), and applies the renderer to the specified layer.
6. THE Map_Viewer_App SHALL register a `get_current_view` tool that returns the current map extent, center point, zoom level, and list of loaded layers with their visibility state.
7. THE Map_Viewer_App SHALL use `app.updateModelContext()` to push the current map state (extent, loaded layers, basemap) back to the model after each modification, so the model has awareness of the current map configuration.
8. THE Dynamic_App_Router SHALL register the app-side tools with `visibility=["app"]` in the tool's AppConfig so they are callable by the running app but hidden from the model's general tool list (the host routes model requests to the app's registered tools automatically).
9. WHEN an app-side tool call fails (e.g., invalid layer URL, layer not found for removal), THE Map_Viewer_App SHALL return an error result with `isError: true` and a descriptive message.

### Requirement 14: Model Context Updates from Map Viewer

**User Story:** As an LLM, I want to know the current state of the map (what layers are loaded, what area is visible) so that I can make informed decisions about what tools to call next.

#### Acceptance Criteria

1. THE Map_Viewer_App SHALL call `app.updateModelContext()` after the initial map render completes, providing the current map extent and basemap name.
2. THE Map_Viewer_App SHALL call `app.updateModelContext()` after each app-side tool call completes successfully, providing the updated map state.
3. THE model context update SHALL include a structured text block containing: current basemap name, center coordinates, zoom level, and a list of loaded layers with their URLs and visibility state.
4. WHERE the host supports image content in model context updates, THE Map_Viewer_App SHALL include a screenshot of the current map view to give the model visual awareness of the rendered state.
